# Build and the OBI vendoring workflow

The build is unusual because the engine is not a normal dependency. `go.opentelemetry.io/obi` is `replace`d to a Git submodule at `.obi-src`, code-generated inside that submodule (eBPF objects need clang), then vendored into this repository. Understanding this loop is a prerequisite for changing anything in the engine.

## TL;DR

- `make vendor-obi` is the composite target: init submodule → generate in Docker → generate test helpers → `go get`/`tidy`/`vendor`.
- `.obi-src` is a Git submodule pointing at a fork of `opentelemetry-ebpf-instrumentation`; on a fresh clone it is empty until `make obi-submodule` runs.
- Builds work from `vendor/` alone — the submodule is only needed to *regenerate* it.
- `make generate-config-schema` regenerates `docs/config-schema.json`; `make check-config-schema` fails the build when it is stale.
- The pre-commit hook is installed by `make install-hooks`, itself a prerequisite of `make prereqs`.

## Mental model

Two directories hold OBI code and they are not interchangeable.

`.obi-src` is a **submodule** — a real Git checkout of the engine's source, at whatever commit this repo pins. It is where eBPF code generation runs (`make generate` and `make docker-generate` both `cd` into it and delegate to its own Makefile).

`vendor/go.opentelemetry.io/obi/` is the **vendored output** — what the Go toolchain actually compiles. It is regenerated by `copy-obi-vendor`, which runs `go get`, `go mod tidy` and `go mod vendor` in sequence.

So the flow for a fork-local engine change is: commit it in the submodule repository → bump the submodule pointer here → run `make vendor-obi` → commit the resulting `vendor/` churn. The HEAD commit of this branch is exactly that shape: it moves `.obi-src` and carries the vendored diff for `api_dependency.go` alongside it.

Editing `vendor/` directly works for a quick experiment and is silently reverted by the next vendoring run.

## Structure / data flow

```
  make vendor-obi
    ├─ obi-submodule        git submodule update --init --recursive
    ├─ docker-generate      cd .obi-src && make docker-generate     (clang / bpf2go)
    ├─ generate-obi-tests
    └─ copy-obi-vendor
          └─ vendor-obi-tests → go get -t ./internal/testgenerated/integration/...
             go get go.opentelemetry.io/obi ; go mod tidy ; go mod vendor
                                   │
                                   ▼
                   vendor/go.opentelemetry.io/obi/**   ← what actually compiles

  make verify  = prereqs + lint-dashboard + vendor-obi + lint + test
  make build   = vendor-obi + verify + compile
```

| Target | Does |
|---|---|
| `obi-submodule` | `git submodule update --init --recursive` |
| `docker-generate` | eBPF/code generation inside `.obi-src` via Docker |
| `copy-obi-vendor` | `go get` + `go mod tidy` + `go mod vendor` |
| `generate-config-schema` | Writes `docs/config-schema.json` from the config struct |
| `check-config-schema` | Diffs the generated schema; non-zero exit when stale |
| `install-hooks` | Copies `hooks/pre-commit` into `.git/hooks/` if absent |

| What | Where |

Build orchestration itself lives in the root `Makefile` (targets listed above) and `.github/workflows/`; neither is citable as a code symbol.

## Sharp edges

- **`vendor/` edits are not durable.** Any fork-local engine change must exist in the `.obi-src` submodule's repository, or `make vendor-obi` erases it. This is the single most common way to lose work in this repo.
- **`make build` re-vendors before compiling.** Running it with uncommitted `vendor/` edits will overwrite them. Use `make compile` for a plain build.
- **Code generation requires Docker and clang.** `docker-generate` shells into the submodule; without an initialised `.obi-src` the target fails immediately.
- **The config schema is CI-enforced.** Adding a field to `pkg/beyla/config.go:Config` without running `make generate-config-schema` fails `check-config-schema` with a diff.
- **`install-hooks` is conditional.** It only copies the hook when `.git/hooks/pre-commit` does not already exist, so an existing hook from another tool silently wins.
