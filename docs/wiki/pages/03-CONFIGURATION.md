# Configuration model

Beyla exposes its own configuration surface — a large `Config` struct with YAML tags and `BEYLA_`-prefixed environment tags — and then converts it into the OBI engine's configuration at runtime. Two structs, one user-facing contract. This page covers how the struct is populated, how it reaches the engine, and what breaks when the two shapes diverge.

## TL;DR

- `pkg/beyla/config.go:Config` is the root type: YAML for files, `env` struct tags for environment variables, and a cached `obi *obi.Config` field holding the converted form.
- Defaults are *derived from OBI's* defaults — `pkg/beyla/config.go:DefaultConfig` starts from `FromOBI(&obi.DefaultConfig)` and overrides only what differs.
- `pkg/beyla/config_obi.go:Config.AsOBI` performs the conversion once and memoises it on the struct.
- Beyla-only fields (Grafana credentials, Sigil export, topology, injector, survey discovery) must be listed as skips in `pkg/beyla/config_obi.go:FromOBI`, or reflection panics.
- A JSON schema for the whole struct is generated by `cmd/beyla-schema` and checked in CI, so adding a field without regenerating it fails the build.

## Mental model

There are two directions of travel and they exist for different reasons.

`FromOBI` runs **once at init**, to seed Beyla's defaults from OBI's. It is the reason a new upstream default automatically becomes a Beyla default. Because OBI's config has no knowledge of Grafana credentials or the injector, those fields are explicitly marked `SkipConversion`.

`AsOBI` runs **at use time**, to hand the engine something it understands. After the mechanical field-by-field copy it calls `overrideOBI`, which is where the Grafana-specific behaviour lives: if Grafana OTLP credentials are configured, the OBI exporter's endpoint resolution is replaced by a closure that consults them.

Environment variables get a third mechanism entirely. `OverrideOBIGlobalConfig` walks the real process environment and *duplicates* every `BEYLA_`/`BEYLA_OTEL_` variable to an `OTEL_EBPF_` equivalent, only when the target is unset. Vendored OBI code reading its own native variable names therefore sees the user's Beyla-prefixed settings without any struct being involved.

## Structure / data flow

```
   obi.DefaultConfig
         │  FromOBI  (reflection, skips Beyla-only fields)
         ▼
   beyla.DefaultConfig()
         │  + YAML file          (-config / BEYLA_CONFIG_PATH)
         │  + BEYLA_* env vars   (env struct tags)
         ▼
   beyla.Config ────────────────► Validate()
         │  AsOBI() [cached]
         │     └─ overrideOBI(): Grafana OTLP endpoint providers + headers
         ▼
   obi.Config  ──► vendored engine

   (separately, at startup)
   os.Environ() ──► OverrideOBIGlobalConfig() ──► duplicate BEYLA_* as OTEL_EBPF_*
```

## Sharp edges

- **`AsOBI()` memoises.** The first call populates the unexported `obi` field and every later call returns that same pointer. Mutating `Config` after the pipeline has started will not reach the engine.
- **Adding a Beyla-only field is a three-place change.** The struct field, a `SkipConversion` entry in `pkg/beyla/config_obi.go:FromOBI`, and a regenerated `docs/config-schema.json` (`make generate-config-schema`). Missing the second causes a panic at startup; missing the third fails the `check-config-schema` CI target.
- **Env duplication only fills gaps.** `OverrideOBIGlobalConfig` sets the `OTEL_EBPF_*` twin only when it is currently empty, so an explicitly-set OTEL-native variable silently wins over its `BEYLA_` counterpart.
- **Several fields are deprecated but still load.** `Exec`, `ServiceName` and `ServiceNamespace` carry deprecation notes in `pkg/beyla/config.go:Config` yet remain wired; prefer discovery-based selection.
- **`Attributes.Kubernetes.MetaSourceLabels` is deprecated and merged at runtime**, not at load — see `pkg/components/beyla.go:buildCommonContextInfo`, which folds it into `ResourceLabels` and logs a one-time warning.
